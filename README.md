Задание 1:
1. Для декомпозиции существующего фронтенда я выбрал Webpack Module Federation по причине, что в данном приложении нет сильно отличающихся функциональностей - нет работы с платежами, сложными формами т.п. Вследствие чего важная особенность Single SPA в виде использования нескольких фреймворков не требуется.

    2. Существующий монолит я решил разделить на следующие микрофронтенды:
        * host - основное приложение Module Federation, которое загружает модули и содержит общие файлы (например, шрифты в пакете vendor)
        * auth - микрофронтенд для работы с авторизацией и регистрацией пользователя. В нем содержатся, соответственно, формы регистрации и входа в приложение.
        * photo - микрофронтенд для работы с местами, фотографиями и лайками. В нем содержится логика работы с фотографиями (загрузка и  удаление) и лайками. Сбор и учет лаков я решил не выделять в отдельный микрофронтенд. В рамках существующего функционала это может показаться избыточным решением, т.к. у лайков сильная зависимость с фото. Но в случае расширения функционала лайков может быть реализовано как отдельное микрофронтендное приложение.
        * profile - микрофронтенд для работы с профилем - создание и его редактирование.

2. Для работы с новыми микросервисами я разбил клиентское приложение на следующие микрофронтенды:
* Микрофроненд товаров - работает с товарами. Получает списки товаров, добавляет, изменяет и удаляет товары пользователя
* Микрофроненд услуг - работает с услугами. Получает списки услуг, добавляет, изменяет и удаляет услуги пользователя
* Микрофроненд аукционов - работает с аукционами. Получает списки аукционов, создает аукциона, подает заявки на аукционы, получает статус аукциона
* Микрофроненд заказов и услуг - позволяет разместить заказ или услугу
* Клиенсткий микрофроненд позволяет зарегистрироваться на площадке, отредактировать профиль клиента, войти в систему (аутентифицироваться и авторизоваться)
* Микрофроненд тех.поддержки - позволяет заявку в тех.поддержку или на апелляцию
* Клиентский микрофронтент, микрофронтенды товаров, услуг, аукционов работают с бэкенд микросервисами через свои BFF (Backend For Frontend). Эти сервисы занимаются роутингом и агрегацией данные для микрофронтедов
3. Монолитный бэкенд я разбил на следующие микросервисы:
* Сервис аутентификации\авторизации - аутентификация и авторизация пользователей, после авторизации пользователи получают JWT токен, содержащий роль пользователя.
* Клиентский сервис - регистрирует пользователя, редактирует его профиль
* Сервис торговых площадок - содержит логику работы с торговыми площадками - регистрация пользователя на площадке, получение списка торговых площадок по заданному фильтру (включая ID пользователя)
* Сервис товаров/ Сервис услуг/ Сервис аукционов - содержит логику работы с товарами/услугами/аукционами. Включает в себя набор CRUD операций для товаров/услуг/аукционов. Сервис аукционов дополнительно публикует событие заявки на оплату аукциона
* Сервис заказов - содержит логику работы с заказами. Включает в себя набор CRUD операций для товаров/услуг пользователя, сбор статистики по заказам, публикации заявки на оплату заказа
* Сервис отплаты - содержит логику работы с оплатой заказов и аукционов. Слушает события новых оплат, по появлению новой инициирует совершение оплаты во внешних сервисах. По итогу операции публикует событие об измененном статусе оплаты.
* Сервис уведомлений - единая точка сбора уведомлений, слушает события и публикует уведомления в нужные топики. Служит для уменьшения связности Сервиса оплат и инициирующих оплаты сервисов
* Сервис техподдержки - содержит логику работы с заявками в тех.поддержку и апелляций. Клиент создает заявки и апелляции, специалист техподдержки  регистрирует эти заявки и обновляет статусы заявок
* Сервис отчетов - формирует отчеты (по продажам и активности пользователей)
4. Для каждого сервиса бэкенда согласно принципу Database rep service создана своя база данных
